# VELORI Supabase Migration Audit

Initial audit date: 2026-10-03. The source-level review below was rechecked against the live project on 2026-10-04.

## Result

The current source does not contain either reported follow-column reference: there are no `followed_id` or `accepted_at` references in the migration chain. The actual relationship contract is `follower_id`, `following_id`, `status`, `created_at`, `responded_at`, and (from migration 110) `updated_at`. Acceptance is represented by `status = 'accepted'`; pending requests use `status = 'pending'`. No `accepted_at` column is needed, and adding one would create a second acceptance source of truth.

Migration 140 made advertisements service-role-only, while the public app reads active placements through PostgREST. Migration 170 restores only the eligible, untargeted, time-windowed, safe-link display fields and continues to deny browser campaign writes. Admin ad and notification panels now use their existing permission-checked Edge API methods instead of bypassing that boundary.

The public-key live verifier reached the configured Supabase project on 2026-10-03 and passes end to end. The social/ad/navigation failures this document originally recorded are resolved. A Management API access token is available in this workspace, so migration history and the private catalog are now queryable through `scripts/db-query.mjs`; the historical "unavailable" notes below are superseded by the Validation Gate section. No production-readiness claim is made beyond the checks recorded there.

## Ordering and Timestamp Findings

The source order is dependency-correct: core/admin foundation precede backend and repair; profile privacy precedes post lifecycle and follow hardening; content management precedes RBAC and admin console; social tables precede their final policy/trigger pass; the ad read repair follows both feature flags and advertisements. The 09120000 privacy migration sorts after 09000000 as intended.

Migrations dated `20261004000000` through `20261018000000` are future-dated relative to the audit date. They were not renamed: deployment history is unavailable, and renaming a possibly applied migration would violate the history-preservation rule. Confirm the linked history before any deployment or timestamp repair. The new 180 migration follows the current source chain and must remain unclaimed as applied until the migration list confirms it.

## Security and Application Contract Findings

- Final follow authorization is based on `follower_id = viewer`, `following_id = target`, and `status = 'accepted'`. Pending rows are private to the participants. The `f.followed_id` and `f.accepted_at` errors are absent from this source tree; if they still appear on a database, they came from SQL outside this checked-in chain or from a stale/manual deployment artifact.
- Reels and stories have parent-row audience policies. The deployed media child policies were found on 2026-10-05 to check parent existence only, so they do not enforce full audience, profile privacy, moderation, and expiry rules on media metadata or signed URL requests. Pending local migration `20261031003500_velori_private_social_media_visibility.sql` adds those checks; until applied and validated, media privacy remains unresolved. The `post-media` bucket is private and Storage reads depend on visible post/media metadata.
- Authenticated users can read their own notifications and update only `read_at`; browser INSERT/DELETE and other UPDATE columns are revoked. Social notification creation is trigger/service-side.
- CMS, navigation, feature flags, announcements, ad management, branding, and admin settings remain service-role managed; public read grants are scoped by RLS and specific display fields where appropriate.
- The public ad panel is now contract-checked for anonymous display reads and denied anonymous writes by both the live verifier and catalog assertion.
- Groups and direct/group messaging are implemented by migrations 190, 260, and 270 and are present in the live schema. The audit verified direct-message send/receipt/delete and the new-chat flow; it did not exhaustively test every group membership and moderation path.
- Admin Reels/Stories moderation endpoints are implemented and permission-checked: `supabase/functions/server/admin-social.ts` serves `GET/PATCH /admin/reels` and `GET/PATCH /admin/stories` with service-role reads and `reels.hide`/`reels.delete`/`reels.restore`/`stories.hide`/`stories.delete` authorization, and `src/app/admin-console/screens/social.tsx` is their console surface. Browser grants were **not** widened; the browser cannot moderate another author's row. One correction was required: the handler mapped a story restore to `stories.restore`, which migration 200 never inserts into `admin_permissions` and no role is granted, so the action was unreachable for every administrator. A story restore is authorized by `stories.hide`.
- Admin system-notification campaigns now have a local delivery path into `notifications` and `system_notification_receipts`, with idempotent per-campaign recipient rows and user preference filtering. Migration 037 and the updated handler remain **not deployed**. The live verifier returned HTTP 400 / `42703` for the newly required timeline/campaign columns and HTTP 404 / `PGRST202` for the dispatch RPC, so live campaign delivery remains incomplete.
- Pending migration `20261031003600_velori_expired_media_storage_cleanup.sql` preserves expired post/story object paths in a service-only queue before parent rows are removed. A service-token-protected Edge Function removes blobs through the Supabase Storage API, and a scheduled GitHub workflow invokes it hourly. These changes are **not deployed or runtime-verified**; automatic media-byte cleanup remains incomplete on the live project until deployment, secret configuration, and a real object deletion check succeed.
- Advertisement impression/click counters have schema columns but no verified increment endpoint/trigger. They must not be presented as real metrics until such an operation exists.
