# Business & Growth schema

Migration: `supabase/migrations/20261107000000_velori_business_growth.sql`.

The migration is additive. It does not alter existing offer, social, auth, or Forge tables. It adds offers and referral structures, specific administrator permissions, server-side RPCs, and triggers. Read-only verification on 2026-10-29 found migration version `20261107000000` in the linked project's ledger and matched all 111 local migration versions to the remote ledger. The migration was already applied; this task did not apply schema changes.

## Tables

### `public.velori_offers`

Server-managed offer configuration: type, eligibility, date window, status, usage limit/count, creator, timestamps, and archival timestamp. Checks constrain enums, title/description size, positive usage limits, nonnegative counts, valid date windows, and archive-state consistency. Indexes support status/date and update-time listing. The Edge Function service role is the only database client granted access; RLS is enabled with no browser policies.

The current app has no checkout/redemption endpoint. `usage_count` is not incremented or exposed as a verified performance metric.

### `public.velori_referral_program`

One boolean-keyed singleton row stores activation, date range, email-verification policy, minimum completed Forge generations, inviter/invitee Forge-token values, and per-inviter, program-wide, and per-user reward caps. It records administrator and update time. The row is locked during qualification so concurrent requests cannot pass caps using the same stale count.

The program is seeded disabled with zero rewards. The admin API rejects enabling it until trusted Android installation verification is implemented and deployed. Positive reward values do not override this safeguard.

### `public.velori_referral_codes`

One code per account. Codes are generated by the database as `VLR-` plus 96 random bits, with a unique constraint, enabled flag, optional expiry, and timestamps. Existing non-admin auth accounts are backfilled. The code is not a bearer credential and can be disabled by an authorized admin.

### `public.velori_referrals`

One row per invitee (`invitee_id` unique) records code, inviter, registration time, status (`pending`, `qualified`, `rejected`), reason, installation verification status/time, and qualification/update times. Installation verification defaults to `unsupported`; the checked status/timestamp constraint and server-only table access prevent browser clients from asserting a verified install. Qualification remains pending unless trusted server-side evidence is recorded. Self-referrals are prohibited by a check constraint. Missing/invalid signup codes do not create attribution via the standard UI; server validation is repeated in the auth trigger. FKs anonymize deleted identities with `SET NULL` rather than preventing account deletion.

### `public.velori_reward_transactions`

The immutable reward history records referral, recipient, reward type (`inviter_forge_tokens` / `invitee_forge_tokens`), positive amount, idempotency key, creation state, and reversal metadata. Unique constraints cover each referral/recipient/type and idempotency key. Rows remain for audit when a user is deleted; the recipient reference is set null.

### `public.velori_referral_events`

Deduplicated lifecycle records capture registration pending/rejected, qualification pending/rejected/qualified, reward issuance/reversal, and failed processing. Events hold a bounded JSON detail object, optional actor, reason, and timestamp. Only the server service role reads or writes these rows.

## Authorization and functions

All five tables have RLS enabled and revoke all privileges from `public`, `anon`, and `authenticated`; only `service_role` receives table access. User operations call narrowly scoped `SECURITY DEFINER` functions with fixed search paths:

- `velori_validate_referral_code(text)` is explicitly granted to `anon`/`authenticated`, returns only validity/reason, and accepts no identity parameter.
- `velori_qualify_my_referral()` and `velori_my_referral_dashboard()` are granted only to `authenticated`; both derive the user from `auth.uid()`.
- `velori_qualify_referral(uuid)` and reward reversal are restricted to `service_role` plus database owner/trigger execution.
- The auth-user trigger issues a referral code and records signup attribution. A successful Forge generation trigger attempts qualification.

Neither the service-role key nor direct table access is exposed to the browser. Admin changes flow through the existing `server` Edge Function, admin-session guard, permission check, and admin audit log.

## Atomic Forge entitlement integration

The existing Forge schema in `20261024232208_velori_forge_studio.sql` defines `velori_studio_accounts.tokens` and the server-side generation reservation contract. Qualification locks the program row, referral row, and both Forge account rows; verifies installation evidence, email/generation eligibility, and caps; then transitions the referral, inserts both idempotent reward transactions, and increments the recipients' `tokens` in one PostgreSQL transaction. A caught processing exception rolls back grants, preserves a pending referral, and records an admin-visible failure event. No Android project or trusted installation-evidence validator is present, so the current migration deliberately leaves install state unsupported and no rewards can qualify.

Reversals lock the selected grant, transition it once, record the administrator and reason, and subtract its exact amount from the same Forge balance. Existing Forge reservation logic will not spend from a nonpositive token balance.
