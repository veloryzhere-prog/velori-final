# VELORI Story Studio — Repository Audit

**Stage:** 1 — repository audit and implementation blueprint  
**Scope:** Story creation and editing only. This document records the current implementation; it does not implement editor changes.

## Executive findings

VELORI currently has two separate story-creation experiences:

1. **`/stories?create=1`** is the existing in-app composer and publisher in [`social-media-pages.tsx`](../src/app/social-media-pages.tsx). It publishes text or one media asset through the existing Supabase story tables and private `story-media` bucket, with an audience selection.
2. **`/stories/create`** is the richer Story Studio in [`story-editor-page.tsx`](../src/app/story-editor-page.tsx). It creates a local editing project, previews and exports media, and now offers a mobile review/publish step that renders each slide and calls the same publisher used by the in-app composer. Computer Studio's existing Export & share presentation is preserved.

At the Stage 1 audit baseline, the richer editor had no general object manipulation workflow or undo/redo. The subsequent Stage 2 implementation added text/sticker/shape selection and transforms, z-ordering, bounded undo/redo, optional shape snapshot data and Canvas2D shape export. The device-selector stage adds two presentations on the same `StoryEditorPage` state: Computer Studio retains the existing controls, while Android / Mobile Studio now prioritizes Media, Text, Sticker and Shape, keeps secondary tools behind More, collapses its storyboard by default, and provides a contextual publish sheet. Freehand drawing/eraser and a full layer manager remain unimplemented. Preview and export still use separate renderers, local draft media references are not durable, and MP4 capability/audio remain browser-limited.

This is a Stage 1 historical audit with a verified implementation addendum. The device presentations are not separate story editors or routes.

The existing backend story model, storage bucket and authorization policies are established and must be preserved. This audit found no evidence that a database migration is needed for an initial editor improvement.

## Repository and route findings

- Stack and scripts are defined in [`package.json`](../package.json): React 19, TypeScript, Vite, React Router, Framer Motion, Supabase JS, Lucide, Node test runner, and Playwright. Story editor helpers have dedicated unit tests. No dedicated canvas package is used by the Story Studio.
- The application route tree in [`routes.tsx`](../src/app/routes.tsx) mounts `/stories/create`, `/stories`, and `/stories/archive` under the existing application shell. The richer editor and the existing Stories page are separate components; they are not alternate views of one shared publisher.
- The Stories page and archive contain `stories_enabled` checks; no equivalent explicit feature-flag check was found inside the standalone `StoryEditorPage`. Confirm intended feature-flag behavior before connecting its publish action. This is an access/gating consistency question, not evidence of a database authorization bypass.
- The richer editor preview in [`Canvas.tsx`](../src/components/story-editor/Canvas.tsx) is composed from DOM elements (including `img`, `video`, text, and sticker layers). The export path in [`export-renderer.ts`](../src/lib/story-editor/export-renderer.ts) renders through Canvas2D.
- Story records, media metadata, visibility, expiration, and private media access are handled by existing Supabase code and policies. The relevant application helpers are in [`social-media.ts`](../src/lib/social-media.ts) and the current social migrations include the story/media tables, bucket restrictions and RLS policies.
- The editor's local collaboration snapshot code is in [`collaboration.mjs`](../src/lib/story-editor/collaboration.mjs). The story types and their current separation are in [`types.ts`](../src/lib/story-editor/types.ts).
- `/stories/create` now presents [`StoryStudioDeviceSelector.tsx`](../src/components/story-editor/StoryStudioDeviceSelector.tsx) on each fresh editor entry. The chosen presentation is ephemeral UI state; the same page still owns and passes the shared scene/history/tool callbacks. See the implementation contract in [`story-studio-device-parity.md`](./story-studio-device-parity.md).
- Authenticated browser checks cover the device choice, chooser cancellation without creating a local project, desktop controls, mobile object creation/undo/redo and viewport rotation. These checks use Chromium viewport emulation, not a physical Android device.
- [`story-studio-mobile-ux-audit.md`](./story-studio-mobile-ux-audit.md) records the mobile hierarchy, publishing mismatch, verified backend boundary and mobile-only redesign direction.

## Evidence labels

- **CODE-VERIFIED** — behavior is directly represented in the current application code; this does not mean it was exercised end-to-end.
- **TEST-COVERED** — a named test asserts the behavior. Test coverage is limited to the assertions made by that test.
- **UNVERIFIED** — no safe test or runtime evidence was gathered in this audit.
- **DEFECT / GAP** — a concrete mismatch or missing capability was found in the code or the executed check.

## Test and runtime evidence gathered for this audit

- **PASS:** `pnpm test` — 130 tests passed, 0 failed. The run includes the existing Story editor helper tests (media, stickers, collaboration, export, text, navigation and templates). These tests do not establish full UI, upload or publishing correctness.
- **PARTIAL / FAIL:** `pnpm e2e -- e2e/qa-matrix.spec.ts --grep "Story Studio reveals one tool at a time and previews the storyboard"` — desktop assertions completed; at the 390×844 phone viewport, the test expected `document.body.scrollWidth` to be 390 but received 432. The mobile test stopped at this assertion. The generated failure screenshot is `test-results/qa-matrix-Phase-4-authenti-ab470-and-previews-the-storyboard-chromium/test-failed-2.png`.
- Existing notes in [`04-stories.md`](./ui-redesign/04-stories.md) and the progress tracker record an earlier pass for this UI test. The fresh failure supersedes the earlier no-overflow claim until reproduced and resolved.
- Story publishing/upload tests that mutate backend data were not run. No story was created or published by this audit.
- Typecheck, production build and full E2E suite were not run as part of this documentation-only audit.
