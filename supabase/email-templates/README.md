# VELORI Auth email deployment checklist

These templates are **not automatically installed** in the connected Supabase project. An administrator with access to the same project as `utils/supabase/info.tsx` must apply them in Authentication → Email Templates and verify the dashboard settings. Never place SMTP credentials, service-role keys, passwords, or live confirmation links in this repository, `VITE_*`, browser code, logs, screenshots, or chat.

Use [the Supabase deployment runbook](../ADMIN_DEPLOYMENT.md) as the single authority for migration order, project setup, bootstrap, and acceptance testing. The notes below cover only template-specific details.

1. In Authentication → URL Configuration, set the Site URL to the real deployed app origin. Use `https://veloryz.online` only if that is the origin actually serving this SPA. Allowlist the exact production, local-development, and test-preview redirect URLs for `/auth/confirm` and `/reset-password`. Do not point production mail at localhost, and verify that every allowed origin serves SPA deep links. Remove stale entries after validation.
2. Enable email confirmation. Configure token expiry, email-send limits, and Auth rate limits in the dashboard. The application uses Supabase-generated, single-use token hashes and does not offer manual OTP/code entry. Test fresh, expired, malformed, consumed, wrong-type, and rate-limited links.
3. Install `confirm-signup.html` as **Confirm signup** with subject `Verify your VELORI account`; use `confirm-signup.txt` as the plain-text body where the dashboard provides a separate text field. Signup and resend set `.RedirectTo` to the exact same-origin `/auth/confirm` route. The template builds the button and fallback from `{{ .RedirectTo }}` and `{{ .TokenHash }}` with `type=email`. That page verifies the token hash only after the person presses **Verify my email**; rendering or prefetching the page does not consume the token. Do not expose `{{ .Token }}`, add code-entry instructions, substitute a handcrafted token, or guess a Supabase confirmation URL. Verify `.RedirectTo`, `.TokenHash`, `.Data.display_name`, and `.Email` with a non-production test account before launch.
4. Install `recovery.html` as **Reset password** with subject `Reset your VELORI password`, using `recovery.txt` as its plain-text body. Install `email-change.html` for the email-change templates supported by the project with `email-change.txt` as its plain-text body. These use Supabase's `{{ .ConfirmationURL }}`. Test secure email change for both addresses if enabled, and test recovery-link prefetch behavior with the mail provider.
5. Configure Authentication → SMTP Settings with an authorized provider and verified sender identity. Enter host, port, username, and password/app password only in protected project settings. HTML branding cannot configure or authenticate a sender. Supabase's default SMTP is for development/testing and must not be treated as public delivery.
6. Apply and reconcile the complete migration sequence using the deployment runbook. Never bootstrap an administrator by editing this template or by copying an Auth user ID into ad hoc SQL; use the protected first-run procedure in the runbook.

This is a static Vite SPA. Session persistence and refresh are handled by Supabase Auth in the browser, authorization remains enforced by database RLS and the protected admin Edge Function, and email/SMTP/dashboard configuration cannot be proven from a frontend build alone.
